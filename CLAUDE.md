# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **self-contained Home Assistant custom integration** (HACS, category `integration`) for Vestel-built smart TVs, controlled over the TV's LAN interfaces. Everything shippable lives under [custom_components/vestel_tv/](custom_components/vestel_tv/); the rest of the repo is documentation.

Platforms: `media_player` and `button` (see `PLATFORMS` in `__init__.py`).

This is a **distribution-only repo**: there is no build system, no dependency manager, no test suite, no linters, no CI. Nothing here is installed or compiled — Home Assistant imports the files as they are. Do not add `poetry`/`uv`/`pytest` commands to docs or assume they exist; if you need that tooling, add it deliberately and update this file.

**Only some of the integration has been run against a live TV** (a `Vestel_MB211`, software 3.33.21.0, sold as ESSENTIELB). Confirmed working on real hardware: SSDP discovery, the WebSocket state channel, the parsed channel list, and key codes — volume up/down were observed changing the TV. Everything else — power, mute, source cycling, text entry, app launching — is implemented against the captured protocol and accepted by the TV, but its *effect* is unconfirmed. Treat those claims as unverified, do not write documentation that asserts a feature works, and keep the caveats in [README.md](README.md) → Status honest.

Git origin is a self-hosted Forgejo instance (`source.tiagoagueda.com`) and is the **only** remote — do not add a `github` remote. `github.com/tiagoagueda/hass-vestel-tv` is a mirror pushed by Forgejo, and it is the URL HACS installs from (HACS custom repositories accept GitHub only), so all user-facing links in docs and `manifest.json` must point at GitHub while all pushes go to Forgejo.

## Versioning & releases

**Only one version number exists**: `version` in [manifest.json](custom_components/vestel_tv/manifest.json). Bump it by hand when you want HACS to offer users an update, and add a matching entry to [CHANGELOG.md](CHANGELOG.md). HACS picks the new version up from a GitHub release (or the default branch).

The minimum Home Assistant version is declared in **two** places that must agree: `homeassistant` in [manifest.json](custom_components/vestel_tv/manifest.json) and in [hacs.json](hacs.json). It is currently `2024.4.0`, set by `ConfigFlowResult` in [config_flow.py](custom_components/vestel_tv/config_flow.py) — raise it if you adopt a newer HA API.

There are **no third-party runtime requirements**: `requirements` in the manifest is empty and should stay that way. `aiohttp` and `voluptuous` are provided by Home Assistant itself, and everything else is stdlib. Do not re-add `websockets` — the WebSocket channel is documented but not implemented, and declaring it makes HA install a package nothing imports.

## Protocol client (`api.py`)

[api.py](custom_components/vestel_tv/api.py) implements the protocol used by Vestel's own **TV Smart Centre** Android app, recovered in August 2026 by packet-capturing that app against a live `Vestel_MB211` (software 3.33.21.0). Keep Home Assistant imports out of it — it must stay a plain async client.

It was previously a port of [T3m3z/pyvesteltv](https://github.com/T3m3z/pyvesteltv). **That design does not work on MB211-era firmware** and was removed in 0.3.0: `POST {app_url}vr/remote` returns 404 on every path tried (including posted directly at the discovered `Application-URL`), and TCP 1986 appears nowhere in a sweep of all 65535 ports — with the TV powered on, and with "Virtual Remote" enabled, toggled, and survived a cold boot. Do not reintroduce either channel on the assumption a setting will open it.

Three channels:

- **SSDP/DIAL discovery** (UDP 1900) — `_DialDiscovery` is an `asyncio.DatagramProtocol` that re-broadcasts an `M-SEARCH` every `DISCOVERY_INTERVAL` (5 s), filters replies to the configured host, and fetches the `LOCATION` URL to read its `Application-URL` header. `discovered` is a freshness check: true only if a reply was resolved within `DISCOVERY_TIMEOUT` (16 s). The resolved `app_url` is the base for every command; with no discovery `_async_post` no-ops at debug level. **The socket pins multicast to the interface that routes to the TV** (`_source_address_for` + `IP_MULTICAST_IF`) — a plain `0.0.0.0` bind finds nothing on a multi-homed host, silently.
- **Commands** — `POST {app_url}SmartCenter` with header `application_name: tv smart centre` and `Content-Type: text/plain; charset=ISO-8859-1`. The TV answers `201 Created` with an empty body. Payloads (note **single** quotes, as the app sends): `<remote><key code='1016'/></remote>` for keys, `<keyboard><key value='116'/></keyboard>` for one character of text, `<command>tvstate</command>` for queries, `<browserseturl><load url='…' page='RC'/></browserseturl>` to launch a portal app. Codes and command names live in [const.py](custom_components/vestel_tv/const.py).
- **State WebSocket** (port 7681) — `ws://host:7681/`, held open by `_ws_loop` with reconnect. **The handshake must send `Origin: http://<host>`**; without it the connection is accepted and then stays silent forever, with no error. Frames seen: `<active_list …>` (the channel list, parsed into `channels`), `<tv_state value='…'/>` (drives `source`), `tv_status:N`. Query replies arrive *here*, never in the POST response — so a client must hold the socket open to read anything back.

Three protocol quirks drive the entity behaviour and must survive refactors:

- **Power-on is one-way.** `KEY_POWER` toggles, and the TV only listens while it is on the network. Turned off with the physical remote it leaves WiFi and is unreachable, so `async_turn_on` can only work if this integration turned it off. Wake-on-LAN is the fix and is not implemented; the wired MAC is in the TV's `dd.xml` if you add it.
- **Source selection has no direct-select.** `async_select_source_step` sends the *source* key once; [media_player.py](custom_components/vestel_tv/media_player.py) loops it up to 10 times until `source` matches — but only when `source` is known, since cycling blind would fire the key ten times for nothing.
- **Volume is write-only.** The protocol offers relative steps and no readable level, so `VestelTV.volume` stays `None` and `volume_level` reports unknown. Do not synthesize a number. The UPnP `RenderingControl` service on port 2870 *looks* like an answer and is not — it accepts `SetVolume`/`GetVolume` perfectly but only governs DLNA casting sessions, and does not move the TV's actual volume.

## Integration architecture (`custom_components/vestel_tv/`)

- [`__init__.py`](custom_components/vestel_tv/__init__.py) — `async_setup_entry` builds a `VestelTV` on HA's shared aiohttp session, starts SSDP discovery, probes the TV's description once so the device registry can be filled immediately, and stores both in `hass.data[DOMAIN][entry.entry_id]` as a `VestelRuntime`. This is the older storage pattern; if you migrate to `entry.runtime_data`, update every platform lookup and the minimum HA version. `async_migrate_entry` handles the v1 (host-keyed) → v2 (MAC-keyed) unique-ID change. A TV that is off cannot describe itself, so `description` may be `None` — never assume it is present.
- [config_flow.py](custom_components/vestel_tv/config_flow.py) — a `user` step (host + optional name) and an `ssdp` step feeding a `discovery_confirm` step. Both validate before creating an entry: they fetch the TV's `dd.xml` via `async_probe_description`/`async_fetch_description` and reject anything that does not answer (`cannot_connect`) or is not a Vestel (`not_vestel`). **Every DIAL device answers the search target registered in the manifest** — Chromecasts, streaming sticks — so `VestelDescription.is_vestel` is what actually filters them, by looking for the fields Vestel adds to `dd.xml` (`verificationKey`, `tv_version`, or `Vestel` in `modelName`). Vestel's own app does exactly this and logs *"non-smartcenter UPnP device msearch is masked"* for the rejects. The unique ID is the **MAC** from `dd.xml` (`format_mac`), falling back to the host for sets that publish none; `async_migrate_entry` in `__init__.py` re-keys version-1 entries and is why `ConfigFlow.VERSION` is 2.
- [entity.py](custom_components/vestel_tv/entity.py) — `VestelEntity` base and `build_device_info`. Every field on the device page comes from the TV's `dd.xml`: `model` is brand + chassis (`ESSENTIELB Vestel_MB211`), `sw_version` is `software_version`, `hw_version` is `tv_version`. Add device-facing fields here, not in a platform, so the media player and every button stay identical.

  **Device grouping across integrations** happens in HA's device registry, which merges entries when *any* `identifiers` **or** `connections` entry matches (`DeviceRegistryItems.get_entries` — "matching identifiers or connections"). Our identifiers are `(DOMAIN, entry_id)` and so are ours alone; the MAC connections are the only thing that can merge this TV with another integration's device. That is why `build_device_info` registers **every** MAC from `description.macs`, not just one: these sets answer on one interface and advertise the other in `<mac>`, so registering only `<mac>` means the TV never groups with the router/DHCP integration that knows it by the `friendlyName` MAC. MACs must be passed through `format_mac` — the registry's `_normalize_connections_validator` raises on an un-normalised stored MAC.
- [media_player.py](custom_components/vestel_tv/media_player.py) — a plain polling `MediaPlayerEntity` (no coordinator) with `SCAN_INTERVAL` from `DEFAULT_SCAN_INTERVAL` (30 s), device class `tv`. `_attr_name = None` with the inherited `_attr_has_entity_name`, so it takes the device name. `play_media` accepts `channel` (typed on the digit keys — there is no direct tune command) and `url` (via `async_load_url`).
- [button.py](custom_components/vestel_tv/button.py) — one `ButtonEntity` per entry in `REMOTE_BUTTONS`, which pairs a translation key with a key code. To add a button, add the code to `const.py`, add the pair to `REMOTE_BUTTONS`, and add the name under `entity.button.<key>.name` in `strings.json` **and all three translations** — they are checked for key parity.
- Config-flow UI strings: [strings.json](custom_components/vestel_tv/strings.json) is the source, but custom integrations are **not** processed by Core's translation build step, so a literal-English [translations/en.json](custom_components/vestel_tv/translations/en.json) (with `[%key:…%]` references resolved) must be shipped and kept in sync, alongside [fr.json](custom_components/vestel_tv/translations/fr.json) and [pt.json](custom_components/vestel_tv/translations/pt.json).

## Conventions

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/). Nothing enforces or automates this here — it is stylistic.
- Code style is `ruff`-formatted (88 cols, double quotes), even though no formatter runs in this repo.
- [custom_components/vestel_tv/brand/](custom_components/vestel_tv/brand/) holds the integration artwork. **This path is load-bearing, not decoration**: since HA 2026.3 a custom integration's `brand/` folder is served by the `/api/brands/…` proxy and takes priority over the brands CDN, which is the only reason the icon appears in the HA UI at all — there is no `vestel_tv` entry on the CDN, so `brands.home-assistant.io/_/vestel_tv/icon.png` returns an "icon not available" placeholder. Never move these into a top-level `images/` folder; that renders in the README but leaves Home Assistant showing the placeholder. The README points at this same folder so one copy serves both.
- The assets are rendered from the official Vestel wordmark — an inline SVG in the site header of [vestelinternational.com](https://vestelinternational.com/), brand red `#DF2228` — to the [brands spec](https://github.com/home-assistant/brands#image-specification): `icon` exactly 256/512 px square, `logo` landscape with its shortest side 256/512 px, both trimmed so no empty edge space remains. The icon is a full-bleed red tile with the wordmark reversed out in white, because the wordmark is 4.6:1 and letterboxing it into a square leaves it an illegible smear at the 48 px the HA UI actually renders. The README carries a trademark notice for these; keep it if you touch the Credits section.
- When extending: keep the wire protocol in `api.py`, keep HA imports out of it, bump `manifest.json` `version` and update `CHANGELOG.md` to release.
